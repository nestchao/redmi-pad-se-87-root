01 — 先给答案

失败有两层原因，而且第二层更致命

如果只看技术，答案很清楚：这台设备上，所有「绕过验证」的路都被密码学关死了， 而所有「利用内核漏洞」的路都被厂商回补掉了。没有原语，就没有下一个动作。

但这不是我们卡住那么久的真正原因。真正的原因是第二层： 因为没有参照物，我们无法区分「这台设备不行」和「我的代码有 bug」。 这两种情况下，日志长得一模一样。

第一层 · 结构性

要拿到 uid 0，必须改变内核里的状态（那一份 cred）。通往内核只有两条路：

  • 从启动链进去 —— 替换/修补内核镜像。被 AVB2.0 签名 + BROM SLA/DAA 挡住，密码学关闭。
  • 从用户态打进去 —— 用一个内核内存破坏漏洞拿任意写。被厂商回补挡住，没有未修补的漏洞。
第二层 · 认知性（真正的原因）

一个 exploit 跑到一半失败，可能是设备不支持、可能是漏洞已修、也可能是你自己的代码写错了三处。 没有一份「在这台机器上确实能跑通」的记录，这三种情况在日志里完全无法区分。 你只能继续瞎试 —— 那几十轮的实际内容就是这个。

Shark 给我们的不是漏洞（第 38 轮我们就已经自己找到 CVE-2026-98260 并打出了 panic）。 它给的是一份参照：同一台设备、同一颗内核，有人跑出过 timers=512 和 uid=0。 从那一刻起，我们的 timers=0 才被判定为「我的 bug」，而不是「设备不行」。
02 — 心智模型

通往 uid 0 的两扇门

这是整件事最重要的一个模型。两条路都通向同一个目标，但被封堵的方式完全不同 —— 而其中一条是数学上不可能，另一条只是暂时没找到。

03 — 关键边界

信任链上，验证在哪里结束

点开每一级看它验什么、谁能通过。注意最关键的一点：验证在内核开始运行之前就已经结束了。 之后系统一路相信自己，再也不检查。

这张图解释了一件事

为什么改内核镜像（门 A）需要伪造签名，而改内核内存（门 B）不需要 —— 因为两者发生在这条时间轴的不同位置。门 A 在验证之前动手， 门 B 在验证之后动手。同一个目标，两种完全不同的难度。

06 — 最大的教训

版本号会说谎

这是最贵的一课。我们的内核是 6.6.118，而几乎所有公开资料都按版本号判断漏洞是否存在。 按版本号，下面两个「当红」漏洞都该是能用的。 但反汇编告诉我们，它们都被提前回补了。

rtmutex 的 remove_waiter() 用 current 而不是 waiter->task，导致内核栈上的 rt_mutex_waiter 悬垂（CWE-416）。 有至少四个公开实现。

官方修复版本Linux 6.6.140
我们的内核6.6.118  ← 按版本号看，早于修复，应该有漏洞

反汇编 remove_waiter（ARM64 上取 current 只有 mrs sp_el0 一条路）：

$ python tools/kcalls.py remove_waiter
=== remove_waiter @ 0xffffffc08106c758  跨度 0x278 ===
  （没有任何 mrs sp_el0）

0xffffffc08106c7d4  bl    rb_erase            ; waiter->tree
0xffffffc08106c7d8  str   x23, [x23]           ; RB_CLEAR_NODE
0xffffffc08106c7dc  str   xzr, [x20, #0x938]   ; 清 pi_blocked_on
                    ; x20 来自 [x23, #0x50] ← 从结构体读，不是从 current
✗
函数内 mrs sp_el0 出现 0 次 ⇒ 不读 current ⇒ 已修复。小米在 6.6.118 里就 backport 了 6.6.140 的修复。

epoll 的 UAF，公开 PoC 成功率达到 约 99%，明确说影响 Android。 这是网上最诱人的一条。

判据一 —— 符号命名（6.6.144 有一系列重命名）：

ep_remove_epi         0xffffffc0804308fc   ✅ 存在
ep_remove_safe        ❌ 不存在
__ep_remove           ❌ 不存在
⇒ 命名是「修复后」的形态

判据二 —— 反汇编 ep_remove：

0x431568  ldr   x20, [x21, #0x30]   ; x20 = epi->ffd.file
0x43156c  ldr   x8,  [x20, #0x18]   ; file->f_count
0x4315a0  ldxr  x10, [x11]        ; ★ atomic_long_inc_not_zero = get_file_rcu()
0x4315ac  stlxr w12, x9, [x11]
0x4315bc  cbz   x20, 0x4316d4       ; ★ pin 失败就跳过临界区
0x4315c8  bl    _raw_spin_lock

✗
epi_fget 内联 + 门控 + fput 配对 —— 完全是修复后的形态。99% 成功率的 PoC 在我们这里一次都不会成功。
不要相信版本号，要相信反汇编。
连 ghostlock419 的 README 自己都写了「OEM 可能提前回补等效修正，不能只依版本字串判定」—— 我们还是亲身体验了一次。
07 — 门 A 为什么永不开

你没法猜出一个签名

门 A 的核心是：你得让 bootloader 相信这个内核是小米签的。 而校验用的是非对称签名 —— 验证只需要公钥（在设备里），签发需要私钥（只有小米有）。 这不是「防护不够好」，这是数学。

动手试一下

假装你要为 boot.img 伪造一个 RSASSA-PKCS1-v1_5 / SHA-256 签名。 下面是需要命中的目标摘要：

target[0:16]9f2a 7c41 e08b 33d5 ...
your[0:16]a17b 3e99 0c44 b2d1 ...
剩下要试1.15 × 1077
已试 0 次

假设你每秒能试 109 次，试完需要约 3.7 × 1060 年。 宇宙年龄约 1.4 × 1010 年 —— 差 50 个数量级。

所以门 A 上的所有努力（刷机脚本、BROM 工具、LK 补丁、各种 MTK exploit） 不是失败了，是不可能成功。我们当时已经知道这一点，但仍在 A 上反复尝试 —— 因为 A 是「看起来最接近」的那条路。

08 — 另一堵墙

BROM：连「进到设备里」都要授权

MTK 平台有一个底层模式（BootROM，BROM），本该是最后的救命通道 —— 它比 bootloader 更底层，很多工具靠它直接读写闪存。 但小米同时开了两把锁。

SLA
Serial Link Authorization
上传 DA（Download Agent）需要签名挑战回应。 没有对应密钥就拿不到可用的 DA。
DAA
Download Agent Authentication
只能加载厂商自己的官方 DA。 自制/通用 DA 一律 0x7017 / 0x7024。
✗
权威文档 penumbra 的 FAQ 原话：「尤其小米……这不是 bug」。 商业工具有授权（Infinity-Box 甚至列了 Redmi-Pad-SE-8-flare），但那是付费门路。

于是整条启动链工具线，全都绕回同一个死循环

工具 / 漏洞它需要什么前提结果
fenrir先解锁 seccfg 才能利用 bl2_ext 未验证反过来依赖解锁
lkpatcher需要 mtkclient（BROM）先解锁绕回 BROM 死路
KamakiriBROM wIndex 越界2023+ 芯片已加边界检查
HeapbaitDA2 堆溢出2024-11 修复，固件 2026-07
Carbonara需要已签名的 DA1DA_HASH_MISMATCH
这五条我们全都认真研究过，其中 BROM 那条读了 penumbra 的全部文档。 它们失败的方式完全一样：都需要一个我们拿不到的前置条件。
09 — 真正的死结

门 A 被数学锁死，门 B 被回补锁死

门 A

需要小米的 RSA 私钥，或付费的 BROM 授权。
不存在等待或努力能解决的路径。
当时没找到

门 B

270 个候选全部已回补。
但「没找到」≠「不存在」。

所以「一直失败」的全部技术原因可以压缩成一句话： 当时我们手里没有任何一个可用的原语，而唯一可能产生原语的那条路，我们无法判断它是否已经走完。

而第 38 轮发生了一件事

在一次尝试中，设备 kernel panic 了。这看起来很糟，但它其实是整段研究里第一个好消息 —— panic 证明那个 UAF 是真实存在的。之后我们陆续做到了：

  • 第 44 轮 —— KASLR 稳定（tracefs raw 记录法，5/5 正确）
  • 第 47 轮 —— 任意写原语逐指令确认
  • 第 57 轮 —— 写出极简第二实现 pwn_min 交叉验证
但这里卡了很久

Stage A（打成 Permissive）能成功，Stage C（改 cred 拿 uid 0）一直失败。 

喷射 234 MB → 直接 reap → 50% 概率 panic

我们当时不知道「必须先确认命中再 reap」。有原语，但收不了尾 —— 而没有任何东西能告诉我们 「收尾本该是什么样」。这就是第二层原因的具体形态。

10 — 转折

Shark 带来的不是漏洞，是参照

路径是这样的：先看到一个文档站，它链了一个 sister project， 在那个项目的设备表里我们看到了一个和内核对逐字符相同的字符串。

内核对齐
我们的设备
Redmi Pad SE 8.7 · MT8786
我们的内核
6.6.118-android15-8-gc4127a25dcf3-ab15863337-4k
Shark 支持列表
6.6.118-android15-8-gc4127a25dcf3-ab15863337-4k
对应的设备
OnePlus Pad2 Pro (OPD2413) · OPPO Find N5 (PKH110) · OPPO Pad4 Pro (OPD2409)
一个非常重要的认识

Shark 从来没有听说过 Redmi Pad SE 8.7。它支持列表里全是 OnePlus / OPPO / Realme / vivo。 它仍然能用，因为 exploit 绑定的是内核二进制，不是设备型号。 我们的平板和 OPPO Pad4 Pro 共享同一颗内核构建 —— 那么能打穿 OPPO 的，就能打穿我们。

它实际给我们的是四样东西

给了什么为什么关键
一个存在性证明 同一颗内核上，有人跑出过 timers=512 并且打到了 uid=0。 「设备不支持」这个假设被直接推翻。
一份可对照的行为基线 上游二进制打印 timers=512，我们自己编译的打印 timers=0。 同一个设备、同一份源码，输出不同 ⇒ 差异只能在我的构建里。 这一步把「玄学」变成了「可定位的 bug」。
一个工程完成的链条 从原语到 ksud late-load 的完整收尾顺序， 以及「第一次失败是正常的」这一条经验 —— 后者直接影响我们会不会在失败后继续。
指向正确的内核构建 这个 exploit 对地址布局极度敏感。 它支持 6.6.118 这条链，等于告诉我们哪些常量对我们有效。
所以「拿到 Shark 之前一直失败」的准确表述是：
我们已经有了漏洞，但缺少一个证明这条路能走完的存在性证据。
没有它，任何失败都可以被解释成「这条路本来就不通」。
11 — 但是

拿到 Shark 之后，还是失败了

这一点很值得记住：Shark 装上之后我们依然没成功。App 一直打印 [calib] timers=0， 而设备上手动跑它的二进制是 timers=512。

真正的原因和启动链、签名、SELinux 全都没关系 —— 是一个21 位的算术错误。

源码假设 KASLR 是 2 MiB 对齐的

exploit 需要在内存里找内核对象，它靠「比对地址的低 21 位」来筛选。 源码假设 KASLR 偏移是 2 MiB（0x200000）的倍数 —— 那样低 21 位就永远不变。 但这台设备的 KASLR 偏移不是。

拖动滑块：KASLR 偏移的低 21 位
0x000000x800000x1000000x180000
源码期望的低 21 位
0x195d48
do_timer_create+0xa8 的链接期常量
内存里实际的低 21 位
0x015d48
（链接值 + 偏移）mod 221
✗
不相等 ⇒ 过滤器一个都匹配不到 ⇒ timers=0 ⇒ 整个链条静默失效，不报错、不崩溃

注意最坏的地方：它不报错。过滤器匹配不到只是返回 0， 程序继续往下走，最后打印一个看起来像「设备不支持」的日志。

修法很小：把四个候选各试一遍，取命中数最多的那个。 

/* 四个候选各试一遍 */
static const unsigned long long cands[4] = {0, 0x80000, 0x100000, 0x180000};
for (int ci = 0; ci < 4; ci++) {
    g_low_adj = cands[ci];
    cc = scan_timer_allocs(...);
    if (cc > c) { c = cc; best_ci = ci; }
}
/* 修复之后 */
[calib] timers=512 low_adj=0x80000
[cred]  task=0xffffff807a40cb00 task_recs=1   ← 从 0 变 1
PROBE_OK
这就是那个参照物的价值

如果没有 timers=512 这份基线，我们的 timers=0 会被解释成 「这颗内核对不上 / 设备不支持 / exploit 已失效」。 有了它，唯一剩下的解释就是「我的代码写错了」 —— 于是我们才去比对那两个十六进制数。

12 — 收尾

三句话

1 · 不要把时间花在密码学上。
门 A 的「不行」是永久的。尽早确认它，然后把全部精力放到门 B。
2 · 不要相信版本号，要相信反汇编。
我们验证过的所有「按版本号应该有」的漏洞，全部已被提前回补。 判据要落在二进制上，而不是字符串上。
3 · 找一个参照物，比再试十遍更有用。
这份研究里最有价值的一次突破，不是发现了新漏洞，而是找到了「同一颗内核上确实能成功」的证据。 它把「这条路不通」和「我的实现有 bug」彻底分开了。
最终结果

修好那 21 位之后，三段链条跑通，bootloader 保持锁定、0 次分区写入： 

$ adb shell su -c id
uid=0(root) gid=0(root) groups=0(root) context=u:r:ksu:s0

$ adb shell grep kernelsu /proc/modules
kernelsu 180224 4 - Live

临时的 —— 重启就恢复。没有任何永久性改动。
